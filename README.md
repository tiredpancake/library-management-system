# Library Management System

A full-stack Library Management System for managing members, books, loans, returns, renewals, reports, fines, transaction tracking, and authentication.

The project uses a React frontend, Spring Boot backend, and PostgreSQL database.

## Members

The Members page is used to manage library members.

Member information includes:

- Membership Number
- Full Name
- National Code
- Birth Date
- Phone
- Address
- Postal Code
- Membership Type
- Status

Membership numbers are generated by the backend.

The system validates member data and prevents duplicate national codes.

The system also keeps a history of changes made to members, including the changed field, old value, new value, user responsible for the change, and change time.

---

## Books

The Books page is used to manage books.

Book information includes:

- Book Code
- ISBN
- Title
- Author
- Category
- Publisher
- Publish Year
- Total Copies
- Available Copies
- Borrowed Copies
- Price
- Status

Book codes are generated automatically by the backend and are 14-digit identifiers.

ISBN is stored as a required text field and is kept separate from the generated Book Code.

When a book is borrowed, the available copy count decreases.

When a book is returned, the available copy count increases.

The system prevents reducing the total number of copies below the number of currently borrowed copies.

Deleting a book is handled as a soft delete by changing its status to `DELETED`.

---

## Loans

The Loans page is used for:

- Borrow
- Return
- Renew
- Check transaction status
- View transaction history

Each transaction has a unique tracking code.

The transaction types are:

```text
BORROW
RETURN
RENEW
```

The transaction statuses are:

```text
PENDING
SUCCESS
FAILED
```

A loan request is first recorded as `PENDING`.

If the operation completes successfully, its status becomes `SUCCESS`.

If the operation fails, the transaction is preserved with `FAILED` status and a user-safe failure message.

This allows the transaction result to be checked later using its tracking code.

Renewals are saved as new transactions and are connected to the previous transaction using `parent_transaction_id`.

This preserves the complete loan chain and history.

---

## Borrowing Rules

Before borrowing a book, the backend checks conditions such as:

- The member must exist.
- The member must not be blocked.
- The book must exist.
- The book must have available copies.
- The member must not exceed the configured maximum number of active loans.
- The member must not have an overdue loan above the configured allowed limit.
- The member's unpaid fines must not exceed the configured limit.
- The member cannot borrow the same book again while that book is still part of the member's current active loan chain.

If all validations succeed, the transaction becomes `SUCCESS` and the available copy count is decreased.

If the operation fails, the transaction becomes `FAILED` and the book inventory remains consistent.

---

## Returns and Renewals

When a book is returned:

- A new `RETURN` transaction is created.
- The return date is saved.
- The returned transaction is linked to the previous loan transaction.
- The available copy count is increased.
- A late return may create a fine.

For renewal:

- A new `RENEW` transaction is created.
- The previous transaction is not modified.
- The new transaction is connected to the previous transaction using `parent_transaction_id`.
- Renewal count is preserved in the loan chain.

Previous transactions remain available in the loan history.

---

## Reports

The Reports page is used to search and filter loan history.

Available filters include:

- Membership Number
- Book Code
- Transaction Type
- Status
- State
- From Date
- To Date

Available states are:

```text
RETURNED
NOT_RETURNED
OVERDUE
```

Results are paginated so that all transactions do not need to be loaded at once.

The backend determines whether a transaction is part of the current active loan chain and uses that information when applying states such as `NOT_RETURNED` and `OVERDUE`.

## Fines

The Fines page shows fines generated by overdue returns.

The table can include:

- ID
- Membership Number
- Loan ID
- Amount
- Paid Amount
- Remaining Amount
- Status
- Created Date
- Paid Date

A fine has an original amount and a paid amount.

Fine statuses are:

```text
UNPAID
PARTIALLY_PAID
PAID
```

The system supports:

- Fine creation for overdue returns
- Configurable fine per day
- Configurable maximum fine
- Partial payment
- Full payment
- Prevention of overpayment

## Transaction Processing

Loan operations use a multi-step transaction flow.

A transaction is first created and committed as:

```text
PENDING
```

The business operation is then executed transactionally.

If it succeeds:

```text
PENDING -> SUCCESS
```

If it fails:

```text
PENDING -> FAILED
```

The tracking code remains available in both success and failure cases.

Business-facing failures may preserve a meaningful message for the user.

Unexpected internal exceptions are converted to a generic public message.

Internal SQL, database, constraint, or stack-trace details are not exposed through failed loan transaction responses.

---

## Concurrency and Transaction Safety

Borrow, return, and renew operations are executed transactionally.

Book inventory updates are protected from conflicting concurrent modifications.

The system prevents two simultaneous requests from successfully borrowing the same final available copy.

The loan transaction chain is also protected against conflicting return and renewal operations.

Integration tests cover:

- Concurrent borrowing of the last available copy
- Concurrent return and renewal
- Inventory rollback on failed operations
- Loan transaction chain consistency

## Database

The project uses PostgreSQL.

The main tables are:

```text
app_user
member
member_history
book
loan_transaction
fine
```

Main relationships:

```text
Member
   |
   v
Loan Transaction
   |
   v
Fine
```

A member can have many loan transactions.

A book can appear in many loan transactions over time.

A loan transaction can have at most one fine.

Renewal and return transactions can reference the previous loan transaction using `parent_transaction_id`.

The main development database is:

```text
library_db
```

## Error Handling

The backend validates incoming requests and returns appropriate HTTP responses.

Unexpected internal exceptions are logged on the server.

The client receives a generic internal error message instead of raw SQL, database, constraint, or stack-trace details.

For operations inside frontend modals, such as borrowing and paying a fine, the error is displayed to the user inside the modal.
